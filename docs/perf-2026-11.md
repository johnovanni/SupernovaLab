# Performance notes, November 2026

Measured 2026-11-12, in-app, with the `--bench` option (see the README). No screen capture was used.

## Result

Spec section 1, success criterion 5: on a recommended system, the 3D view runs at 50 fps or better, and all
instrument panels redraw at 30 fps or better while the timeline plays. The recommended class includes Intel Iris Xe.

| Build | 3D view (GL frames drawn) | WPF composition frames (a proxy for panel redraws) | Frame interval p95 / worst | Target |
|---|---|---|---|---|
| Debug | 94.5 fps | 94.5 fps | 14.4 ms / 26.2 ms | Met |
| Release | 79.0 fps | 79.2 fps | 16.5 ms / 29.6 ms | Met |

Setup common to both runs (the two launches were not identical, see below):

- Preset Betelgeuse (the last preset the sweep in the same launch loaded), main window 1366x768, Instruments window open.
- The Instruments window showed the schematic spectrum (visible panel) and the pulse train (radio panel). These are the
  two views that redraw as time moves, so this is the worst case for the panels.
- The whole timeline (13.5 decades) played once over 20 s, 0.675 decades per second. The run reached the end of the
  timeline both times.
- Each result is one run of 20 s. They were not repeated, so run-to-run spread is not known. Earlier Debug runs during
  development, with the same method, gave 74 to 92 fps (task reports 15 and 16).

The Release build was not faster than the Debug build here. The frame rate is probably limited by the GPU and by WPF
composition, not by the app's own code. This was not investigated.

A full resample of all six panels (any input change) took about 50 ms in the Debug test run (Task 15), so dragging a
slider updates the panels about 20 times a second. The gravitational-wave strain, at 8,192 samples per second, is the
largest single cost.

## Machine

- GPU: Intel Iris Xe Graphics, driver build 30.0.101.1960, OpenGL 4.1.0 (the log says "4.1.0 - Build ..."; that it is a core-profile context is inferred from the requested context). This comes from the app's own log:
  `Intel | Intel(R) Iris(R) Xe Graphics | 4.1.0 - Build 30.0.101.1960`.
- Windows 11 Pro (10.0.26300).
- CPU model and RAM were not recorded by the app, so they are not stated here.

## Windows on screen or off

The bench places the main and Instruments windows off-screen, to the left of the whole virtual screen. WPF still lays
them out and renders them, and the GL view still draws. But the compositor may do less work for a window nobody can see.
So an on-screen run could be a little slower. This was not measured on-screen.

## Not measured

- **The spec section 1 minimum hardware class** (Intel UHD 620 class graphics, 2 cores, 8 GB) was not measured. No such
  hardware was available. The results above say nothing about whether the minimum class meets the targets.
- Higher resolutions (1920x1080 and larger) were not benchmarked. The 3D view's frame rate is likely to fall with its
  pixel count.
- The frame rate is the rate the app rendered frames, not a display refresh rate.

## The two launches

- **Debug launch:** four presets, main and Instruments windows rendered to PNG first, then `--sweep 54` and `--bench 20`.
  It ran before the GPU line was added to `bench.log`, so the GPU name comes from the Release launch (same machine).
- **Release launch:** two presets, main window only, then `--sweep 54` and `--bench 20`.

## What "panels redraw" means here

The panel figure is the count of WPF composition frames (`CompositionTarget.Rendering`). That event fires every frame
whether or not a panel repainted, so it is an upper-bound proxy for the panels' redraw rate, not a direct measure of it.

## Project 2

### Task 4: GPU particle renderer and HDR pipeline (milestone-1 performance test)

Measured 2026-11-12, in-app, with `--snapshot ... --size 1366x768,1920x1080 --quality high,medium,low --bench 20` in one
Release launch (six 20 s runs, no screen capture). Same machine as above (Intel Iris Xe, OpenGL 4.1.0 Build 30.0.101.1960).
The scene is drawn into an RGBA16F target, then a 5-level dual-filter bloom, ACES tone map and gamma. The debris are the
temporary isotropic particle set (|v| uniform in volume over 0.7 to 1, seed 1987) drawn by `ParticleRenderer`; the
layered velocities arrive in Task 6, so these figures are for the particle count and the pipeline, not for the final shaders.

| Build | Quality (particles) | Size | 3D view (GL frames drawn) | WPF composition frames | Frame interval p95 / worst | Target (50 fps) |
|---|---|---|---|---|---|---|
| Release | High (200,000) | 1366x768 | 69.2 fps | 69.2 fps | 20.2 ms / 41.9 ms | Met |
| Release | Medium (100,000) | 1366x768 | 75.8 fps | 75.8 fps | 16.7 ms / 33.1 ms | Met |
| Release | Low (50,000) | 1366x768 | 76.7 fps | 76.9 fps | 16.1 ms / 33.7 ms | Met |
| Release | High (200,000) | 1920x1080 | 69.7 fps | 69.9 fps | 19.4 ms / 33.5 ms | Met |
| Release | Medium (100,000) | 1920x1080 | 70.4 fps | 70.7 fps | 19.6 ms / 31.7 ms | Met |
| Release | Low (50,000) | 1920x1080 | 66.3 fps | 66.6 fps | 21.4 ms / 41.6 ms | Met |

Setup: lab defaults (no preset), Instruments window open off-screen with the visible panel on its spectrum and the radio
panel on its pulses, the whole timeline (13.5 decades) played once over 20 s per run, each run reached the end. Each cell is
one run, not repeated, so run-to-run spread is not known. The three levels differ by little (Low at 1080p was the slowest), so the
runs do not separate them. HDR pipeline: on (RGBA16F worked) in every run.

**Ruling:** High (200,000 particles) is at least 50 fps at 1366x768 with the Instruments window open, so High is the default.
The fps ceiling of about 70 to 77 fps looks like the WPF composition/display rate rather than the GPU: the particle count
barely moves it. The tone-map exposure was tuned after the bench (1.0 to 0.2, to stop the 30-day debris ball clipping to
white); exposure is a uniform, so it does not change the cost of the passes.

### Task 11: breakout flash, limb darkening, jet glow, quality governor

Measured 2026-11-12, in-app, with `--snapshot ... --size 1366x768,1920x1080 --bench 20` in one Release launch (the snapshots first, then two 20 s
runs; no screen capture). Same machine as above (Intel Iris Xe, OpenGL 4.1.0 Build 30.0.101.1960). Every Milestone 3 layer is in the scene: layered
particles, cutaway and cut faces, shocks and shells, wind haze and dense shells, pulsar wind nebula, SN 1987A's rings, now also the breakout flash
(a full-screen additive pass, drawn only during breakout), the jets at 4x and the retuned intensities.

| Build | Quality (particles) | Size | 3D view (GL frames drawn) | WPF composition frames | Frame interval p95 / worst | Target (50 fps) |
|---|---|---|---|---|---|---|
| Release | High (200,000) | 1366x768 | 67.4 fps | 67.4 fps | 20.8 ms / 43.0 ms | Met |
| Release | High (200,000) | 1920x1080 | 63.7 fps | 63.9 fps | 23.1 ms / 52.3 ms | Met |

Setup: default quality (High), Instruments window open off-screen with the visible panel on its spectrum and the radio panel on its pulses, the
whole timeline (13.5 decades) played once over 20 s per run, each run reached the end. The preset loaded was SN 2023ixf (the last preset of the
snapshot list that ran before the bench). The quality governor was off for the run (`SceneController.AutoQuality = false`, as for every
`--snapshot` run), so the figures are for the quality asked for. One run of each; run-to-run spread is not known. Task 4's rows for the same two
sizes at High were 69.2 and 69.7 fps (a different preset, before the layered shaders, shells, rings and the flash existed), so the Project 2 additions together cost about
2 to 6 fps on this GPU at these sizes. The flash itself is one extra full-screen triangle for a few seconds to hours of source time, so it does not
show in a 20 s timeline run. The 1920x1080 flash/bloom cost at I = 8 was not measured separately.

The quality governor (`QualityGovernor`, ruling R-P2-30) steps High, Medium, Low when the mean GPU render time over 3 s of frames is above 20 ms
(GL_TIME_ELAPSED queries around the scene's drawing, read a few frames late so the CPU never waits). It never steps up by itself. If the timer queries
cannot be created or fail, it stays off and only the View > Quality menu changes the quality. It was tested with fed render times (30 Hz intervals with
small render times never step down; over 20 ms for 3 s steps down once); it did not trigger in the run above, and the queries' real readings were not logged.
