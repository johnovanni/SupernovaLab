# Performance notes, November 2026

Measured 2026-11-12, in-app, with the `--bench` option (see the README). No screen capture was used.

## Result

Spec section 1, success criterion 5: on a recommended system, the 3D view runs at 50 fps or better, and all
instrument panels redraw at 30 fps or better while the timeline plays. The recommended class includes Intel Iris Xe.

| Build | 3D view (GL frames drawn) | WPF composition frames (a proxy for panel redraws) | Frame interval p95 / worst | Target |
|---|---|---|---|---|
| Debug | 94.5 fps | 94.5 fps | 14.4 ms / 26.2 ms | Met |
| Release | 79.0 fps | 79.2 fps | 16.5 ms / 29.6 ms | Met |

Setup common to both runs (the two launches were not identical, see below):

- Preset Betelgeuse (the last preset the sweep in the same launch loaded), main window 1366x768, Instruments window open.
- The Instruments window showed the schematic spectrum (visible panel) and the pulse train (radio panel). These are the
  two views that redraw as time moves, so this is the worst case for the panels.
- The whole timeline (13.5 decades) played once over 20 s, 0.675 decades per second. The run reached the end of the
  timeline both times.
- Each result is one run of 20 s. They were not repeated, so run-to-run spread is not known. Earlier Debug runs during
  development, with the same method, gave 74 to 92 fps (task reports 15 and 16).

The Release build was not faster than the Debug build here. The frame rate is probably limited by the GPU and by WPF
composition, not by the app's own code. This was not investigated.

A full resample of all six panels (any input change) took about 50 ms in the Debug test run (Task 15), so dragging a
slider updates the panels about 20 times a second. The gravitational-wave strain, at 8,192 samples per second, is the
largest single cost.

## Machine

- GPU: Intel Iris Xe Graphics, driver build 30.0.101.1960, OpenGL 4.1.0 (the log says "4.1.0 - Build ..."; that it is a core-profile context is inferred from the requested context). This comes from the app's own log:
  `Intel | Intel(R) Iris(R) Xe Graphics | 4.1.0 - Build 30.0.101.1960`.
- Windows 11 Pro (10.0.26300).
- CPU model and RAM were not recorded by the app, so they are not stated here.

## Windows on screen or off

The bench places the main and Instruments windows off-screen, to the left of the whole virtual screen. WPF still lays
them out and renders them, and the GL view still draws. But the compositor may do less work for a window nobody can see.
So an on-screen run could be a little slower. This was not measured on-screen.

## Not measured

- **The spec section 1 minimum hardware class** (Intel UHD 620 class graphics, 2 cores, 8 GB) was not measured. No such
  hardware was available. The results above say nothing about whether the minimum class meets the targets.
- Higher resolutions (1920x1080 and larger) were not benchmarked. The 3D view's frame rate is likely to fall with its
  pixel count.
- The frame rate is the rate the app rendered frames, not a display refresh rate.

## The two launches

- **Debug launch:** four presets, main and Instruments windows rendered to PNG first, then `--sweep 54` and `--bench 20`.
  It ran before the GPU line was added to `bench.log`, so the GPU name comes from the Release launch (same machine).
- **Release launch:** two presets, main window only, then `--sweep 54` and `--bench 20`.

## What "panels redraw" means here

The panel figure is the count of WPF composition frames (`CompositionTarget.Rendering`). That event fires every frame
whether or not a panel repainted, so it is an upper-bound proxy for the panels' redraw rate, not a direct measure of it.

### Task 14: final benchmark, with the guided tour running (spec criterion 5)

Measured 2026-11-13, in-app, Release build, one launch: `--snapshot ... --preset default,sn1987a --size 1366x768,1920x1080 --bench 20 --bench-tour --quality high`

not repeated. The quality governor was off (as in every snapshot run); its GPU measurement was logged.

|---|---|---|---|---|---|---|---|
| default (9 stops, 81 s) | 1366x768 | 46.7 fps | 69.9 fps | 67.0 fps | 20.9 ms / 49.2 ms | 0.89 ms / 5.9 ms | Met while travelling |
| default | 1920x1080 | 45.1 fps | 67.1 fps | 65.2 fps | 21.6 ms / 53.0 ms | 2.11 ms / 8.3 ms | Met while travelling |
| SN 1987A (12 stops, 99 s) | 1366x768 | 43.9 fps | 67.1 fps | 65.1 fps | 23.2 ms / 54.0 ms | 1.10 ms / 10.0 ms | Met while travelling |
| SN 1987A | 1920x1080 | 41.5 fps | 62.3 fps | 62.8 fps | 22.9 ms / 61.3 ms | 2.19 ms / 7.0 ms | Met while travelling |

Reading the table:

- **"While travelling"** is the time the timeline moves between stops (about 45 to 51 s per run): this is where the view animates, and it is the
  figure that corresponds to the earlier playback benchmarks (63 to 70 fps). It meets 50 fps at 1366x768 (about 67 to 70 fps) and at 1920x1080 (62 to 67 fps).
- **"Over the whole tour"** is lower (41 to 47 fps) only because the 3D view redraws on demand. While the tour dwells on a stop (4 s each) nothing moves, so
  it draws about 17 to 19 times a second (the cutaway stops orbit slowly; the others are static). Those frames are not slow: the WPF composition rate stays at
  about 63 to 67 fps throughout. The 50 fps figure is therefore claimed for the moving view, not as a count of GL draws across a dwell on a static picture.
- **The governor's GPU render time is plausible on this Iris Xe.** The mean is 0.9 to 2.2 ms per drawn frame (max 5.9 to 10.0 ms), against a 15 ms frame
  interval at 65 fps and the governor's 20 ms threshold. So the GPU is far from the limit and the frame rate is bound by the WPF composition/display
  rate (about 65 to 70 fps), as in the earlier runs. 1920x1080 costs about 2.4 times the GPU time of 1366x768 (pixel count ratio 2.25) and still
  leaves a large margin. The governor did not trigger (it was off for the run); its timer queries returned readings on every drawn frame.
- A first attempt of this launch did not start the app's tour clock (the snapshot run skips it), so the tour never advanced and the figures were
  discarded; the clock is now started for `--bench-tour` and the table above is from the second launch. (That made three launches for this task, one over its budget of two.)
- Not measured: the minimum hardware class (Intel UHD 620), an on-screen window, repeat runs.

### Task 16: cut faces draw Rayleigh-Taylor fingers, tongues and ragged boundaries

The cut-face fragment shader now evaluates, per pixel, a 1D value-noise fbm for each layer boundary it is near (3 octaves), and inside a
mixing cone's chord a 2D edge fbm (2 octaves) plus, per finger and tongue of that cluster, one 1D value noise for the wavy centreline
(at most 5 fingers and 4 tongues per cone). Uniforms: three vec4 arrays (10 clusters, 50 fingers, 40 tongues), set per face.

`--snapshot <dir> --window main --size 1366x768 --quality high --cutaway --bench 20 --preset "default@2592000+cutaway,default@31560000+cutaway,sn1987a@7344000+cutaway,casa@1849000+cutaway"`
(Release build, same machine; the bench plays the whole timeline with the last preset, Cas A, the cutaway on, Instruments open off-screen):

|---|---|---|---|---|
| final shapes | 75.8 fps | 75.7 fps | 17.2 / 37.3 ms | 1.02 / 7.69 ms |
| first shapes (same shader cost, other widths) | 74.9 fps | 74.8 fps | 17.3 / 37.6 ms | 1.10 / 8.46 ms |

The cutaway stays well above 50 fps (Task 7's cutaway bench, a different preset: 57.9 fps). One run each, not repeated; the faces cover a
small part of the 898x612 view at this zoom, so a zoomed-in cutaway costs more per frame (not measured).

Task 16 fix round 1 (plumes with sheaths, clumpy stalks, heads, undulating boundaries; 2 or 3 plumes per cone, three noise fields per
pixel inside a cluster), same command and machine: **69.2 fps** (3D draws 69.3 fps; frame interval p95 19.6 ms, worst 70.5 ms; GPU render

Task 16 round 2 (ruling R-P2-35: small fingers along every layer boundary on the whole face, plus 1 or 2 broad plumes per cone), same

| Size | Frames / 20 s | Frame interval p95 / worst | GPU render time mean / max |

the cutaway meets the 50 fps target with room to spare. One run.

Notes on the numbers:

- The governor's own run (the app's real behaviour) settles at 1/2 or 1/4: the 1/2 level's GPU time (11.3 to 11.7 ms) sits just under
  P3-9's 12 ms threshold, so whether it steps on to 1/4 depends on spikes (it did at 1366x768, not at 1920x1080).
- **Unexplained per-frame cost (a hypothesis, not measured).** The frame interval is longer than the two views' timed GPU work by a
  nearly constant amount: about 13 ms at 1/1 (43.5 ms interval against 30.4 ms timed, 1366x768), 12 ms at 1/2 (24.9 against 13.0)
  and 10.6 ms at 1/4 (16.0 against 5.4). A roughly fixed cost per frame, outside the timer queries, is the likeliest reading. Its
  suspects are not separated by this run:
  - WPF composition of a second GL control (each control's frame is copied through the D3D interop);
  - the GPU switching between the two GL contexts;
  - UI-thread CPU work per frame: the Instruments window redrawing its two moving views, the timeline restating both scenes
    (`ExplosionScene.At`, the Close-up's environment state), the panels;
  - the antivirus scanning the freshly built exe on its first launch (it slowed such a launch by about 40% in Project 2).
- **Proposed baseline (one launch, the owner's or the controller's decision):** the same command with `--bench-baseline` instead of
  the level matrix, which runs at each size: the Close-up **hidden** (not drawn and not composed: the main view alone with the same
  Instruments load), the Close-up **shown with the lensing pass and environment capture off** (the cost of a second GL window
  alone), and the Close-up at **1/4** (the lensing on top). Launched a second time after a first launch of the same build, so the
  antivirus is out of it. Comparing the three separates the second window's fixed cost from the lensing's.
  `--bench-baseline` exists (review fix round 1; parse-tested, not yet launched):
  ```
  SupernovaLab.App.exe --snapshot <dir> --preset sn1998bw --size 1366x768,1920x1080 --bench 20 --bench-spin 0.9 --bench-baseline
  ```
- This was the first launch of a freshly built exe; an earlier first launch (Project 2, Task 16) ran 40% slow from an antivirus scan.
  Here the frame rate follows the lensing level closely (23 / 40 / 62 fps) while the main view's GPU time stays flat, so the
  lensing cost is real, but some of the shortfall may be that disturbance. One run each, not repeated.
- Spin 0.9 is the case the bench was asked for; spin 0 (every placeholder outside the bench) was not measured. P3-7's
  lookup-table fast path would help spin 0 only, not this case.
- The two GL controls have separate contexts (GLWpfControl may share object lists; nothing here relies on sharing): each window
  makes its own renderers.

  antivirus scan is the likely cause, but it was not measured. Task 4's numbers were also from a first launch and may carry some
  of it. The final bench below shows no such state: its markers run at 72 to 77 fps.
- **The fixed per-frame cost is the UI thread's render pass: about 10 to 11 ms at 1366x768 with the main view alone** (the repeat
  runs). The main GL control's OnRender is 3.7 to 3.9 ms of it, of which the app's drawing is only 0.6 ms. The other 3.1 ms is
  GLWpfControl's D3D interop, which waits for the GPU to finish the frame. The view models' time step is about 1.3 to 1.7 ms (a
  temporary xUnit loop, Debug build, not kept). The rest, about 5 to 6 ms, is WPF's own layout and rendering of the windows; it
  was not split further. Hiding the Instruments window saves about 0.3 ms.
- **Each GL control blocks the UI thread until its GPU work is done**, so the two views' GPU times add to the frame instead of
  overlapping. The Close-up at 1/4 takes 6.5 ms of UI time for 4.25 ms of GPU work; with its lensing off it still takes 2.1 ms
  (the second control's interop: the "second GL window" cost). Task 4's frame interval minus the timed GPU work (11 to 13 ms) is
  this render pass. So the fix is to give the Close-up less GPU work per frame, and fewer frames.

### Step 2: the speed-ups (ruling R-P3-10, and the proposals R-P3-11 to R-P3-13)

- **R-P3-10, the cached ray map.** `lensing.frag` (the same tracer, `u_output = 1`) writes each ray's fate and exit direction (or
  surface hit point) into an RGBA32F ray map. `lensing_shade.frag` colours it from the environment every frame (one texel fetch
  and one cube-map sample per ray); the upsample is as before. A `RayMapPlanner` retraces only when the camera, spin, surface
  radius, grid switch, viewport or level change: the whole map at the moving level while the camera moves. Once it stops, the
  finer still level is built behind the shown map in bands of rows (scissor test) of about 4 ms of GPU each; the band size follows
  the measured cost per ray. Without RGBA32F the pass falls back to Task 4's direct trace every frame.
- **R-P3-11, the Close-up drawn on demand while the timeline plays.** A time step asks for a Close-up frame only when the state
  record or a drawn menu switch changed, or when ruling P3-6 calls for an environment capture (past its 0.005 log step and outside
  its 4-per-second cap). A capture held back by the cap is asked for by a later time step, or drawn when playback stops. With a
  still camera the Close-up now draws about 8 frames a second while the timeline plays (each capture, and GlHost's second frame),
  not every frame.
- **R-P3-12, Auto holds 50 fps.** The governor still steps down above 12 ms of GPU time (P3-9). It now also steps down when the
  frames it is fed average more than 20 ms apart while the lensing takes more than 2 ms of them (the GPU time adds to the frame, as
  above). It is fed only frames that traced a whole map (a moving camera), and only under Auto.
- **R-P3-13, Auto's still level is full resolution.** With the map cached, a still view costs the same at any level, and the
  refinement is spread over frames. So Auto refines to full when the camera stops; the governor sets only the moving level.
